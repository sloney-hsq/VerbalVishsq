Date: 2026-10-15
Repository: standalone checkout root

## Scope and result

The standalone runtime metadata and CI dependency flow are reproducible for the requested targets:

- `.python-version` is `3.11.14`.
- `.nvmrc` is `20.19` (Node 20.19.x).
- `frontend/package.json` declares `engines.node` as `>=20.19 <21`.
- `pyproject.toml` constrains Python to `>=3.11,<3.12`.
- `requirements.txt` remains the manually maintained top-level dependency range.
- `requirements.lock` is generated from `requirements.txt` with uv, contains transitive pins and hashes, and is universal for Python 3.11-compatible platforms.
- CI installs `requirements.lock` with `--require-hashes`, then installs the project with `--no-deps -e .`; the frontend continues to use `npm ci`, `npm test`, and `npm run build`.
- `frontend/package-lock.json` root metadata is synchronized with `frontend/package.json`; its root `engines.node` is exactly `>=20.19 <21`. No dependency versions or registry URLs were changed.

Both commands succeeded. On Windows, pip correctly skipped the lock's Linux-only `uvloop` entry because its environment marker did not match.

## Cross-platform risks

- The lock is generated with `--universal`, so platform-specific artifacts are represented with environment markers and hashes. Linux CI will install `uvloop`; Windows correctly skips it. Native packages such as DuckDB, httptools, pydantic-core, PyYAML, rpds-py, and websockets still depend on an available wheel for the selected Python/OS/architecture.
- Local verification used Python 3.11.14 on Windows. CI uses Ubuntu and must retain the lock's Linux markers and hashes; changing the lock without rerunning uv can make `--require-hashes` fail.
- Node 20.19.x is required by metadata. Running npm under Node 24 only produced a warning locally; it is not evidence of Node 20 compatibility, which CI enforces through `.nvmrc`.
- The frontend build's chunk-size advisory is non-failing and unrelated to dependency resolution.
